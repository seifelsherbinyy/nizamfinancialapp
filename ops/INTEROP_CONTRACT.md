# NIZAM interop contract — the one document both repositories read

> **Status:** IN FORCE. Authored 2026-08-10 under spec `06-two-agent-vps` task 10.16, owning
> requirement **R31**, on the owner's clarification of the same date.
>
> **What "clone and migrate both repositories" means.** It means making the two agents *understand
> each other* — feeding information and communicating. It is **not** a code migration and **not** a
> repository move. Neither repository ever holds the other's code. This document is the whole of what
> they share about how they talk, and it is deliberately written so that it is **applicable from the
> other side without this repository being present**: every shape it needs is written out here rather
> than referred to by an import.
>
> **Where it lives, and how the other side reads it.** `ops/INTEROP_CONTRACT.md`, in the finance
> repository, which is public — so the other side references this path rather than holding a copy. A
> copy would be a second authority that could drift, and the failure mode of a drifted interop contract
> is two agents each behaving correctly by a different rule.
>
> **Nothing below is invented here.** Every rule already exists, in `.kiro/steering/two-agent-vps.md`,
> in PFOS contract 12, or in code in one of the two repositories, and each is cited where it is stated.
> Where this document and the cited source disagree, the source wins and this document is the bug.

## 0. The two parties, and what they do not share

| | Finance agent | Life agent |
|---|---|---|
| Repository | this one | the other one |
| Runtime | Node + TypeScript (steering §1) | Python (FastAPI) (steering §1) |
| Store | `finance.db`, its own volume | `life.db`, its own volume |
| Model key | its own, its own weekly bound | its own, its own weekly bound |
| Environment file | `finance.env` | `life.env` |
| Bot | one of the two | the other of the two |

They share **four** things and nothing else: this contract, the envelope document
`nizam-signalbus.envelope.schema.json`, the host, and the provider account (through two separate
keys). **They share no code**, and that is by design rather than by neglect — steering §1 records the
polyglot decision and its reason, which is that there will never be a second implementation of money.

**Phase 1 is one agent, and that is authorised.** Option **(b)** of the owner mandate §7 is in force:
phase 1 ships the **finance agent** on its bot alone; the other bot stays created, hardened and
**idle**. Nothing in this contract changes when the second agent arrives, which is the point of writing
it before the second agent exists.

## 1. The envelope is the SOLE channel

Steering §4.2: *the bus is the only channel. Cross-agent data flows exclusively through the signal bus,
which is append-only, internal-network-only, and never exposed through the proxy.*

There is no second route. Not a shared file, not a shared table, not a socket, not a queue, not an
environment entry read by both, not a log one side tails. If a fact needs to cross, it crosses as an
envelope or it does not cross.

### 1.1 The stored envelope — eight fields, and no ninth is possible

Wire names are authoritative; they are what travels. The dialect is JSON Schema 2020-12. Both forms
close themselves (`unevaluatedProperties: false`), so **an unrecognised key is refused, never ignored**.

| Field | Form | Rule |
|---|---|---|
| `signal_id` | string, 1-128 | unique, generated by the **producer** |
| `ts` | string | the producer's completion time, `YYYY-MM-DDTHH:MM:SSZ`. **The only temporal field in the envelope** |
| `producer` | enum | `life` \| `finance` |
| `kind` | enum | `money_pressure` \| `recovery_state` \| `readiness` \| `budget_breach` |
| `tier` | enum | `money_safe` \| `life_safe` |
| `consent_scope` | enum | `shared` \| `producer_only` |
| `payload` | object | see §1.2. Closed, `level` required |
| `hash` | string, 64 lowercase hex | `sha256` over `ts` + `producer` + `kind` + `payload`. **Computed by the bus, never submitted by the producer** |

Two forms, and the difference is exactly one field:

- the **draft** (write) form requires the first seven and **forbids `hash`**. A producer that submits
  one is refused with `hash_asserted_by_producer`: integrity is the bus's claim about what it stored,
  not the producer's claim about its own payload;
- the **stored** (read) form requires all eight. Validation runs on write **and again on read**, so a
  later schema change cannot silently make historical rows readable in a shape the current rules forbid.

`kind` is a **closed set**. Adding a member is a schema change to the vendored document, reviewed on
both sides, and never a runtime string.

### 1.2 The payload — three keys

```
payload: { level: "green" | "amber" | "red",        // required
           direction: "downshift" | "hold" | "upshift",   // optional
           note: string, maxLength 120 }                  // optional
```

That is the entire payload vocabulary. A `level` is a level and not a magnitude; a `direction` is a
direction and not a delta.

## 2. The band-not-figure rule

Steering §4.3: *the state crosses, the data never does.* A payload may carry a direction or a level. It
may **not** carry a balance, a due date, an account identifier, journal text, or any free text over 120
characters — **and the field does not exist**, so leakage is not possible by construction.

**"Does not exist" is stronger than "is filtered", and the difference is the whole design.** A filter
is a piece of code that can be bypassed, mis-ordered, or forgotten on a new path. An absent field
cannot be populated by any caller on any path. So the four rules below are refusals at the schema, and
each has its own reason code so that an operator learns *which* rule fired:

| Rule | Reason code | What it refuses |
|---|---|---|
| No magnitude | `field_numeric` | any numeric-valued field, anywhere in the envelope |
| No second clock | `field_temporal` | any field naming or shaped like a date or a deadline, other than `ts` |
| No pointer | `field_identifier` | any field naming an account, a transaction, a document, a payee, a reference, a code |
| Closed object | `field_unrecognized` | any key the schema does not declare |

And the note is fenced separately, because it is the one field that holds text:

| Rule | Reason code | Note |
|---|---|---|
| Capped | `note_exceeds_cap` | **refused, never truncated** — truncating would silently ship the first 120 characters of something that was never allowed to leave |
| No figure in prose | `note_carries_a_figure` | **a digit anywhere in a note is refused.** A note that needs a digit is not directional |

The canonical example, from the architecture document: finance publishes `money_pressure: amber`. It
never publishes what it would take to say *how much*.

**For the other side, concretely.** Compute the band locally, from local data, and publish the band. Do
not compute a band from a figure the other side sent you, because the other side cannot send you one.

### 2.1 The refusal vocabulary, in full

A write is refused with exactly one of these, and the refusal carries the reason, the **path** where the
rule fired, a port-level code, the producer's own `signal_id` when the input carried a usable one, and
the **length** of a note when one was present. **It has no field for the offending value**, and there is
no quarantine: a refused envelope is not retained anywhere.

```
envelope_not_an_object   envelope_field_missing   payload_not_an_object
field_numeric   field_temporal   field_identifier   field_unrecognized
signal_id_invalid   ts_not_utc_instant   producer_not_a_member
kind_not_a_member   tier_not_a_member   consent_scope_not_a_member
level_not_a_member   direction_not_a_member
note_not_a_string   note_exceeds_cap   note_carries_a_figure
hash_asserted_by_producer   hash_missing   hash_malformed   hash_mismatch
```

Implementation on this side: `src/server/signals/envelopeValidation` (`envelopeValidation.ts`). The
other side validates the same vendored document in its own language and must produce the same
decisions; it need not produce the same codes, but it should, because a shared vocabulary is what makes
an operator able to read one audit line and know which side refused.

## 3. The address: `BUS_INTERNAL_ENDPOINT`

**It is the only address either side dials.** Not a hostname, not a URL, not a port on the host.

The accepted shape is `<INTERNAL_SERVICE_NAME>:<PORT>` and nothing else. Each side reads it from its own
environment file; there is no default, and an unreadable value **refuses the boot** rather than being
repaired — the only available default would be "somewhere nobody said". Eight shapes are refused, and
each one is a way a service ends up reachable from somewhere it must not be, or unreachable by the only
containers that must reach it:

| Refusal | What it catches |
|---|---|
| `endpoint_empty` | nothing configured |
| `endpoint_carries_a_scheme` | implies a route through something that speaks one; no internal service here has a proxy route of any kind |
| `endpoint_carries_a_path` | the same mistake, spelled as a route on a shared host |
| `endpoint_host_absent` | a port with nothing in front of it |
| `endpoint_host_not_an_internal_name` | an address literal or a wildcard — not a name an internal network resolves, and a wildcard is the first half of the exposure R9 forbids |
| `endpoint_host_reserved` | a name that resolves to the container **itself**: a bus each client would find inside itself |
| `endpoint_port_absent` | no port, or a non-numeric one |
| `endpoint_port_not_in_range` | outside the protocol's own bound |

Implementation on this side: `src/server/process/internalEndpoint` (`internalEndpoint.ts`), shared by
the bus and the scheduler so there is exactly one spelling of the rule. **The parser is not the
isolation** — the network layer does that: `ops/docker-compose.yml` marks the internal networks
`internal: true` and gives the internal services no `ports:` key at all. What a process can contribute
is a refusal to be *repointed*, and that is all this is.

## 4. The two routes the bus serves

This is the part the other side cannot infer and cannot work without. The method is `POST`. There are
**two** paths and no others. Bodies are JSON. The inbound body bound is 64 KiB.

### 4.1 `POST /publish`

Body: **a draft envelope** exactly as §1.1 defines it — the seven fields, no `hash`.

| Answer | Status | Body |
|---|---|---|
| stored | `200` | `{ outcome: "stored", signalId, hash, storedAt }` |
| refused by a field rule | `200` | `{ outcome: "refused", reason, at, code, signalIdRef, noteLength }` — `reason` is one of §2.1 |
| duplicate identifier | `200` | `{ outcome: "refused", reason: "signal_id_already_stored", at: "signalId", code }` |

A refusal is an **answer**, not a transport error: it arrives as `200` with a refusal body, because the
request was understood and declined. Note what the refusal body does not contain: the value.

### 4.2 `POST /read`

Body: a **query**, and only the four keys the port declares.

```
{ subscriber: "life" | "finance",     // required — who is asking. The bus decides what that answers to
  limit: non-negative integer,         // required
  kind: one of the four kinds,         // optional
  since: string }                      // optional — lower bound on the envelope's own `ts`
```

There is deliberately **no `producer` filter**, even though the store supports one: the port declares
none, and admitting one here would be a second read vocabulary that the consent rules would have to be
re-reasoned about.

| Answer | Status | Body |
|---|---|---|
| delivered | `200` | `{ outcome: "delivered", signals: [ stored envelope, … ] }` |
| refused by consent | `200` | `{ outcome: "refused", reason }` — see §5 |

**A refusal is not an empty list.** The two are different shapes on purpose, so a caller cannot conflate
"you may not see this" with "there is nothing here" even carelessly.

### 4.3 The protocol-level refusals

Before any domain rule is reached:

| Refusal | Status |
|---|---|
| `service_shutting_down` | `503` |
| `body_over_bound` | `413` |
| `method_not_permitted` | `405` |
| `route_unknown` | `404` |
| `body_not_json`, `query_not_an_object`, `query_subscriber_not_a_member`, `query_kind_not_a_member`, `query_since_not_a_string`, `query_limit_not_a_count` | `400` |
| `store_unavailable` | `503` |

`store_unavailable` on a read means a stored row no longer validates, or a served value would have
breached a de-identification claim. It is deliberately **not** a shorter delivered list: silently
dropping a row would turn a corrupt store into a quiet one.

Implementation on this side: `src/server/process/busServer` (`busServer.ts`), and the append-only store
under `src/server/signals/` (`signalStore.ts`).

## 5. Consent: two independent gates, evaluated on every read

Steering §4.5 and requirement **R8**.

- **Scope.** `consent_scope: producer_only` means the **producer may read its own signal and nobody
  else may**. Refusal reason: `consent_scope_producer_only`. `producer_only` is the **default for any
  new kind** until the owner explicitly widens it, and the widening list is currently **empty** — so
  today, every kind is producer-only and a cross-agent read is refused. That is the fail-closed
  starting position, not an oversight: a kind becomes shared when someone decides it should, in a
  recorded change, and never by a field being mis-set.
- **Tier.** A subscriber reads only the tiers it is permitted. Refusal reason:
  `tier_not_readable_by_subscriber`.

The two gates are **independent, not nested**: both are evaluated, from the **stored** envelope, on
**every** read. Nothing is decided once at write time and trusted afterwards. Where the stored scope and
the kind's default disagree, the **narrower** wins, so a mis-set field can never widen a kind by
accident.

Implementation on this side: `src/server/signals/consentGate` (`consentGate.ts`).

## 6. What never crosses at all

**The other repository's most restricted classification — the one whose egress set is empty — never
reaches this deployment.** Requirement **R10**, steering §4.4. Its own repository declares that
classification and its egress set in `PRIVACY_CLASSIFICATION.json`; the material it covers is excluded
from the deployment **entirely**, rather than admitted and then handled carefully.

*This document does not name that classification, and that is a rule rather than a style choice.*
Contract 12 §4.4.3 forbids any artifact in this tier from naming, counting, summarizing or **pointing
at** such content, and a checker holds it over `ops/**` — so the classification is named only in the
governing documents that forbid it, and nowhere in the deployment's own artifacts. The other side knows
which classification this is, because it is the one that side declares.

**The exclusion is enforced twice, and the second is the one that binds.** Its egress set excludes it at
source, in the other repository. And the envelope's `tier` enum has exactly **two** members,
`money_safe` and `life_safe`: the excluded classification **is not a member of the union**, so a signal
claiming it fails validation as an unknown enum member (`tier_not_a_member`) rather than being filtered
somewhere later. There is no value either side could set to mark a signal as carrying it, which is why
this is an exclusion and not a filter — there is no code path that handles such content, and no test
that exercises carrying it. The only test is that an attempt to introduce it is refused.

## 7. Isolation, which the bus does not weaken

Steering §4.1 and requirement **R17**:

- **Separate stores.** `life.db`, `finance.db`, `signals.db`. **No process opens another agent's
  store**, and no cross-store attachment on an existing connection, ever. The bus is not an exception:
  it owns `signals.db` and opens neither agent's store.
- **Separate keys and separate bounds.** Each agent's model key and weekly bound are reachable only
  under that agent's own identity. A compromise of one yields nothing of the other. This holds at the
  **file** level (each service reads one environment file and no other) and at the **configuration**
  level (the other agent's entry names are never spelled).
- The bus is where both agents' state meets, and it therefore holds **no credential of any kind**.

## 8. The bus authenticates nothing, and that is deliberate

**Do not "fix" this by adding a credential.**

The control is **reachability**, not a secret. The bus binds an internal name on an internal network; it
has no published port, no proxy route, and no path from the internet or from the host. Only the
containers on that network can address it at all, and they are the two agents.

A credential would make the posture **worse**, not better, and for three reasons worth writing down so
that nobody has to re-derive them:

1. it protects a port that would still be reachable while it was attacked — the reachability control
   does not have that property, because there is no route to attack;
2. it is a secret with a lifecycle: it must be generated, placed in two environment files, kept equal
   between them, and rotated — four new ways for the deployment to be wrong, in exchange for guarding a
   route that does not exist;
3. this repository is **public** (steering §0b), so every new secret is a new thing that must never
   appear in a tracked file.

What the bus does instead of authenticating is **decide what each subscriber may see**, from the stored
envelope, on every read (§5). Identity is a claim in the query, and the bus treats it as a claim: it
grants nothing on the strength of it that the consent rules do not grant.

The append-only store plus its audit mirror is the accountability record — every accepted signal and
every refusal, with its reason, its path and its code. That is a stronger record than an access log,
and it is why the bus emits no log line of its own.

## 9. How the other side acquires its half

Three change specifications, under `ops/nizamcore-patches/`:

| File | What it specifies |
|---|---|
| `001-fastapi-wrapper.patch` | wrap the existing update handler in an application the topology can start, and add the health endpoint the orchestrator probes |
| `002-dedup-per-bot.patch` | make de-duplication keyed per **bot**, so two bots emitting the same update identifier are both processed |
| `003-signalbus-egress-target.patch` | add the bus as an egress target, so the life agent can publish and read |

**They are change specifications, not applicable diffs, and this is stated rather than implied.** The
other repository was never read from this session — steering §6 permits a read-only clone or fetch and
forbids a modify or a push — so there are **no verified context lines and no blob hashes, and none were
invented**. Anyone applying them works from the specification and the surrounding code as it actually
is, in a session opened on that repository. `ops/nizamcore-patches/` carries the apply order, the
expected test deltas, and how to verify each one.

## 10. Reading the other repository, and writing to it

Steering §6, as amended by task 10.1's read-only carve-out (§2a):

| Operation | Posture |
|---|---|
| `git clone` / `git fetch` of the other repository | **permitted** — it is a read. It must land at a path **outside this repository's tracked tree**, so nothing it brings can be committed here by accident |
| reading its files, once cloned | permitted, when a task needs to see it |
| modifying it, committing in it, **pushing** it | **owner-gated.** Not permitted without the owner's explicit authorisation |

The permission to read is not an instruction to exercise it. As of this document, the other repository
has **not** been cloned, fetched, read, modified or pushed by any session on this side, and the three
change specifications remain **emitted and unapplied**.

## 11. What this contract does not do

It does not make the two agents one system. It does not give either side a view of the other's data. It
does not define a shared schema for anything except the envelope. It does not authorise the finance
agent to compute a life fact, or the life agent to compute a monetary one — and on that last point the
rule is older and firmer than this document: **the model tier never sources a monetary number** (steering
§4.5); the deterministic engines do, on their own side of the boundary, from their own store.

The capability-by-capability division of the full NIZAM scope across the two bots — including which
capabilities need a signal, which band, and which are **refused by construction** because they would
need a figure to cross — is `ops/AGENT_CAPABILITY_SPLIT.md`. Read it next.
